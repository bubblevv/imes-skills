# BDJB 脚本合并为存储过程

在“审核/取消审核前增加下游单据拦截”且用户要求少脚本时读取本参考。目标是把同一前置校验收敛为一个无结果集存储过程，再让现有 `BDJB` 前置规则调用它；不改变审核主流程、下游数据或客户端资源。

## 1. 先固定问题边界

建立一张简短 case card：

- 目标数据库、实例、生产/测试分类（未知就记录 `unknown`）；
- 单据可见名称、`BDJB_PJLX`、命令（审核或取消审核）；
- 用户给出的下游单据名称、示例单号和要求的业务错误文本；
- 请求是调查、生成脚本还是部署。只读 MCP 只能调查，不能部署。

先执行 `SELECT DB_NAME(), @@SERVERNAME`，再按项目固定路由连接。不要从目录名、默认连接或另一个客户环境推断数据库。

## 2. 源码只翻固定入口

对动态单据的 BDJB 生命周期，优先定位以下入口；入口已经闭合后不要继续全库搜索：

1. `CBill::SetTrigArray`（及 `CBillSimple::SetTrigArray`）：确认活动规则查询、`BDJB_QZJC` 分类，以及排序键。当前客户端按 `BDJB_QZJC, BDJB_ORDER` 读取规则，`QZJC=1` 放入前置检查，`QZJC=0` 放入实际执行列表。
2. `CBill::ExeCmd` / `CBillSimple::ExeCmd`：确认前置检查、主 SQL、后置 SQL 的执行事务、错误处理和回滚行为。前置过程抛出严重级别 16 的业务错误即可中止整笔操作。
3. 源码中的占位符替换：常见有 `@SJDH`、`@FLH`、`@USERCODE`、`@USERNAME`。客户端是文本替换，不是参数绑定；字符串单号在 BDJB 文本中必须保留引号，例如 `EXEC dbo.ProcName '@SJDH'`，替换后才是合法 SQL。
4. 对旧规则使用 `rg` 搜索精确字段/过程名，再读取相邻源码和活动 `BDJB` 行。不要一开始扫描全部 `sys.sql_modules`。

把源码事实和业务假设分开记录。若多个字段都可能表示“已存在/已审核”，先用目标数据和规则 SQL 证明，不要猜。

## 3. 关系证据和规则顺序

下游关系必须同时由三类证据闭合：

- `BDJB` 旧规则给出的主表、明细表和现有审核状态条件；
- `sys.columns` 证明所有连接列真实存在且类型可比较；
- 一条真实数据链证明“下游明细来源单号/来源分录号 -> 上游明细 -> 下游表头单号”的方向。

关系通常按“来源单号 + 来源分录号”连接明细，再按下游单号连接下游表头。不要只按单号连接而丢失分录粒度，也不要因为 ER 图上的 `FK` 标记自行发明目标列。

把每个候选规则写成矩阵：规则 ID、命令、`QZJC`、顺序、目标/来源、每个谓词及其实际匹配数。若用户要求“只要存在下游检验单就不能撤审”，不得擅自加 `SHBZ=1`；是否按审核状态过滤必须由旧规则或用户业务定义证明。

若同时存在多类下游单据，用户指定的专用提示应先判断；原有通用下游拦截随后判断，以保持旧行为且让专用错误不被通用错误遮蔽。

## 4. 存储过程形状

过程应满足：

- 参数类型以实际业务单号列为准，长度足够但不猜字段名；
- `SET NOCOUNT ON`，不返回 `SELECT` 结果集；
- 每个阻断条件用 `IF EXISTS`，命中后 `RAISERROR(N'...', 16, 1); RETURN;`；
- 使用 schema-qualified 表名和列名；不需要动态 SQL；
- 先放用户要求的专用下游检查，再放保留的原有检查；
- 过程只做校验，不在其中更新审核标志、删除下游单据或回写数量。

专用错误文本应逐字保留用户确认的内容。不要把业务错误吞掉、改成 `PRINT`，也不要用 `TRY/CATCH` 转成成功返回。

## 5. 单文件部署脚本

“一个存储过程”仍需要一个 BDJB 调用接入点；推荐交付一个 SQL 文件，文件内按以下顺序组织：

1. 数据库/实例门禁；
2. 表和列存在性门禁；
3. 过程已存在时 fail-closed，要求人工核对，避免静默覆盖；
4. 精确保存旧 `BDJB_SQL`（包括 CRLF、空格和大小写），确认 `BDJB_ID/命令/QZJC/顺序/启用标志/备注` 唯一匹配；
5. `CREATE PROCEDURE`；
6. 在事务中把旧 BDJB 文本替换为唯一的 `EXEC dbo.<procedure> '@SJDH'`，并断言 `@@ROWCOUNT=1`；
7. 最后查询过程定义和 BDJB 行用于人工核对。

`GO` 只用于批分隔，不能当作事务提交。若过程创建与 BDJB 更新分成批次，脚本失败后应依靠“过程已存在”门禁阻止盲目重跑；不要用 `CREATE OR ALTER` 掩盖未知存量定义。读写数据库前必须重新确认身份并取得明确授权，禁止通过只读 MCP 部署。

## 6. 生成前后验证

生成前：

- 只读查询目标表列、旧 BDJB 文本和下游关系计数；
- 至少找一个“有专用下游、无其他更早通用下游”的真实单号，验证专用提示能被命中；
- 再找一个无任何下游的单号，验证过程应直接返回；
- 静态检查文件中只有一个 `CREATE PROCEDURE`，没有临时调试结果集或额外过程。

授权部署后：

- 读取 `OBJECT_DEFINITION`/`sys.sql_modules`，确认过程文本；
- 读取 `BDJB_ID`，确认只改成过程调用且原有字段未变；
- 在获准测试环境分别执行“有下游”和“无下游”路径，确认错误文本、事务回滚和零结果集；
- 用客户端真实取消审核冒烟，确认前置过程在审核标志更新前执行；
- 生产环境仍只通过批准的部署通道执行，不用数据库 MCP 写入。

## 7. 重启后“消失”的排查

重启电脑不会删除已提交的 SQL Server 过程或 `BDJB` 行。若重启后看不到配置，按此顺序核对：

1. 查询 `DB_NAME()`、`@@SERVERNAME`，排除连到了另一实例/数据库；
2. 查询 `OBJECT_ID`、`sys.sql_modules` 和目标 `BDJB` 行，区分数据库对象与客户端缓存；
3. 检查之前是否只生成了本地脚本、只改了内存配置，或执行在未提交事务中；
4. 检查客户端是否从配置文件/更新缓存重新覆盖了本地设置。

不要把“重启后不可见”直接归因于 SQL Server 自动回滚；先用身份和对象查询证明实际状态。

## 交付检查清单

- [ ] 目标身份已确认，环境分类已记录。
- [ ] 源码入口、占位符替换和 `QZJC/ORDER` 顺序已确认。
- [ ] 上下游连接列来自真实 schema 和数据证据。
- [ ] 专用检查先于通用检查，错误文本逐字正确。
- [ ] 一个过程、一个 SQL 文件，BDJB 调用已 guarded update。
- [ ] 旧 BDJB 文本精确匹配，影响行数断言为 1。
- [ ] 生成前验证未写库；部署状态在交付中明确说明。
